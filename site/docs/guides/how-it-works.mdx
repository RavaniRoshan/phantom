## One task, four components

| Component | Responsibility |
|---|---|
| **Windows app** | Composer, task list, live VM view, approvals, history, settings. |
| **Control plane** | Authenticated local API; owns tasks, events and approvals. |
| **Agent + daemon** | Neutral action schema, decision loop, policy, run store, audit chain. |
| **Guest agent** | Runs inside the VM's interactive session; captures and injects. |

## The loop

1. The GUI submits a task to the control plane.
2. The daemon queues it, creates a run record, and starts an agent.
3. Each step asks the configured provider for one neutral action (`DecideAction`).
4. The action is checked against the capability scope, executed, and observed.
5. A fresh screenshot and text context return to the model for the next step.
6. Before `done`, the verifier checks the task's criteria. Failure triggers a bounded re-plan.
7. Every step is written to SQLite and appended to a SHA-256 hash chain.

## Why capture works here

The host never calls `PrintWindow` on a VM window. The in-guest agent captures the
**real console display** with Windows.Graphics.Capture or a GDI fallback, rejects
all-black frames, and returns a PNG with its dimensions. Coordinates are in the
screenshot's pixel space; browser actions explicitly use CSS viewport pixels.

## Observability

The GUI streams `events` over SSE: task created, step, outcome, approval needed,
error and VM status. Screenshots are saved as task artifacts so you can replay what
the agent saw.
