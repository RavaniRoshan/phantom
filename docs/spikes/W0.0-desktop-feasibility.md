# W0.0 — Hidden-desktop feasibility spike (go/no-go)

**Status:** NOT CONCLUSIVE — requires a real interactive Windows session.
**Owner:** Rust/platform engineer.
**Gate:** Per `docs/DEVELOPMENT-PLAN.md`, **no W1 desktop investment before this
decision is recorded.** If the spike fails, W1 is replaced by an isolated-VM /
Cloud PC workstream (+4–6 weeks).

## Question

Can `CreateDesktopW` reliably drive the v1 app matrix while the user's
foreground session is untouched?

## Protocol

1. On a real Windows session, run each app below on a `CreateDesktop` desktop:
   Notepad, Chrome (native, not CDP), Excel, Explorer, and a dialog-heavy app
   (Settings / a WinForms dialog).
2. For each app, drive a scripted sequence: launch → wait-for-window →
   screenshot → click a known control → type text → screenshot → close.
3. Record the metrics below per app. Each app is pass only if **all** of its
   boxes are green on 3 consecutive runs.

| Metric | Pass threshold |
|---|---|
| Click accuracy (intended control receives the click) | 20/20 |
| Text-entry success (text appears in target control) | 20/20 |
| Capture validity (non-black, correct target window, PNG magic) | 100% |
| UIA hang rate (no call exceeds 2 s) | 0 hangs |
| Input reaches target (not the user's foreground window) | 100% |
| Background invariant (user focus/clipboard/pointer untouched) | 100% |

## Runner

```powershell
cargo run -p phantom-desktop --example desktop_smoke
# then extend to Chrome/Excel/Explorer/Settings and record results here
```

The runner must write a per-app pass/fail table into this file and leave no
orphan `cmd.exe` / desktop handles after each app.

## Observation from the agent workspace (2026-11-18)

An attempt to run `desktop_smoke` in this agent environment **hung for >180 s**
and left an orphan `cmd.exe` host process on the hidden desktop (manually
killed; the host process is started by `VirtualDesktop::launch_named`). No
per-app data was produced.

This is **not** a definitive failure: this environment has no interactive
Windows desktop, so `SetThreadDesktop` + `PrintWindow` + `ShellExecuteW`
cannot be expected to behave as they would on a real session. It does show the
path is fragile and must be validated before W1.

## Critical observation — foreground leak (2026-11-18, operator report)

While the smoke test ran, the operator observed **Notepad created in the
foreground on their real screen**. This is a direct violation of the
background invariant ("the user's foreground window is never disturbed") and
of the hidden-desktop premise itself.

The `open()` path was subsequently changed to launch app targets with
`CreateProcessW` + `STARTUPINFO.lpDesktop = WinSta0\PhantomDesktop` (rather than
`ShellExecuteW`, which cannot set the target desktop). If the leak persists
after that fix, the conclusion is unambiguous:

> **`CreateDesktopW` cannot reliably isolate target apps on this machine.**
> Decision: **broad** — replace W1 with the isolated-VM / Cloud PC workstream
> (DEV-PLAN fork: +4–6 weeks, re-scope W8). Do not proceed with the narrow
> supported-app matrix.

This does not yet rule out that a properly-bound hidden desktop could work on
a different Windows build/session; it does rule out shipping the current
approach without a real fix. Treat the leak as a blocker, not a passing result.

## Debug pass 1 — lpDesktop binding (operator asked for one more attempt)

Hypotheses for the foreground leak:
1. `ShellExecuteW` accepts no `lpDesktop`, so the target was launched on the
   user's default desktop. **Fix:** app targets now use `CreateProcessW` with
   `STARTUPINFO.lpDesktop` (URLs still use `ShellExecuteW`).
2. The desktop path was hard-coded as `WinSta0\<name>`. If this agent process
   is in a different window station (service/non-interactive), that path points
   at the wrong station. **Fix:** the station name is now queried at runtime
   via `GetProcessWindowStation` + `GetUserObjectInformationW(UOI_NAME)` and
   stored on `VirtualDesktop`; all child launches use `<actual-station>\<name>`.
3. `SetThreadDesktop` may silently fail on a thread that already owns windows.
   **Diagnostics added:** log the station name and whether `GetThreadDesktop`
   matches the created desktop after binding.

Re-run pending. If the target still appears on the foreground screen, treat
the spike as FAILED and take the isolated-VM fork.

## Debug pass 2 — results (3 runs, operator watching)

| Run | Fix applied | Result |
|---|---|---|
| 1 | baseline (`ShellExecuteW`) | Notepad appeared on operator's **foreground screen**; `open()` succeeded but `find_window()` saw nothing. |
| 2 | `CreateProcessW` + explicit `lpDesktop`, runtime station name | Notepad no longer observed on foreground; `find_window()` now finds a window, but `PrintWindow` returns an **all-black** frame. Both screenshots fail. |
| 3 | + `PW_RENDERFULLCONTENT` + `CREATE_NO_WINDOW` | Still **all-black**. Operator was not sure whether a console popup appeared (GUI runs now paused at their request). |

Leaked `notepad.exe` / `ping.exe` processes were cleaned up after each run;
`VirtualDesktop::close()` only terminates the keep-alive host, not the target
app — a separate leak to fix in the VM workstream.

**Conclusion:** the current `CreateDesktopW` approach fails the spike on two
counts: (a) the foreground leak in the baseline, (b) **all-black capture in all
three runs**, including with `PW_RENDERFULLCONTENT`. The black-capture root
cause is not established (candidate: hidden desktops are not painted by DWM,
or `find_window()` selects a non-app window), but the release gate requires a
valid non-black observation, so this is a hard fail for the narrow path.

**Decision: BROAD — take the isolated-VM / Cloud PC fork.** Replace W1 with an
isolated-VM workstream and re-scope W8 packaging (+4–6 weeks per DEV-PLAN).
Do not invest further in hidden-desktop capture.
