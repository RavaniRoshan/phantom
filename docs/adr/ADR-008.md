# ADR-008 — Isolated VM / Cloud PC replaces the hidden desktop

**Status:** Accepted (2026-11-18)
**Work item:** task 17 (replaces W1)
**Context:** W0.0 spike failed (see `docs/spikes/W0.0-desktop-feasibility.md`).

## Context

Three smoke runs showed the `CreateDesktopW` approach cannot satisfy the
release gates: the baseline leaked the target app to the user's foreground, and
after fixing the launch binding every capture was all-black, including with
`PW_RENDERFULLCONTENT`. A trustworthy observation is a hard requirement.

## Decision

1. Desktop actions execute **inside an isolated Windows VM** (Hyper-V local VM
   or Windows 365 Cloud PC), never on the user's session.
2. Foreground isolation becomes **structural**: the VM is a separate OS
   instance, so the user's focus/clipboard/pointer cannot be disturbed.
3. Capture and input use the VM's own console/agent channel (RDP or a guest
   agent), producing valid frames because the VM has a real display.
4. `phantom-vm` defines a typed backend abstraction (create/acquire, capture,
   input, destroy) so local Hyper-V and Cloud PC are interchangeable. A mock
   backend supports CI without VM infrastructure.
5. W1 (hidden desktop) is cancelled. W1.1–W1.8 capabilities are re-scoped into
   the VM workstream where they still apply (window targeting, UIA/SoM, app
   profiles). Packaging (W8) must include VM provisioning/connection setup.

## Consequences

- +4–6 weeks per the development plan; GA moves out accordingly.
- The user's machine is never driven directly — the safety argument is much
  simpler than a policy-only boundary.
- VM lifecycle, cost and pool sizing become first-class concerns (W6/W8).
- The existing `phantom-desktop` crate is retained only as a legacy/unsupported
  path; new work targets `phantom-vm`.
