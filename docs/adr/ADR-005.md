# ADR-005 — Coordinate contract: client-area pixels with explicit screen mapping

**Status:** Accepted (target; implementation tracked in W1.2 — not yet landed)
**Work item:** W1.2
**Context:** DEV-PLAN §6; W0.0 spike; W1.1/W1.2.

## Context

The current desktop input path is ambiguous and unsafe:

- `click()` falls back to `PostMessageW(hwnd, WM_LBUTTONDOWN, WPARAM(0),
  LPARAM(0))` — it always clicks client coordinate `(0, 0)` regardless of the
  requested point.
- `MOUSEEVENTF_ABSOLUTE` is not set on the injected click, so `SendInput`
  interprets coordinates as relative motion.
- The capture is taken from whatever window `find_window()` enumerates first,
  not the window the action targeted.
- There is no single defined coordinate space, so a model cannot reliably
  ground a click.

## Decision

1. **One coordinate space:** all desktop coordinates in observations and
   actions are **client-area pixels of the target window**, origin at its
   client `(0, 0)`, with the mapping to screen coordinates computed explicitly
   via `ClientToScreen`.
2. **Targeted actions:** a `window` param selects the target by title/class/
   process; `list_windows` exposes candidates. `PrintWindow` captures the
   selected target, not an arbitrary enumerated window.
3. **Correct input injection:** `SendInput` uses `MOUSEEVENTF_ABSOLUTE` with
   normalized screen coordinates; `PostMessage` includes packed `x`/`y` in
   `LPARAM`. The `LPARAM(0)` / self-`BitBlt` paths are removed.
4. **Return the mapping** (window rect, client offset, DPI scale) in the
   observation so the model can reason about grounding.
5. **Per-monitor DPI awareness** and native-scale capture, with a documented
   downscale cap for the model (W1.8).

## Consequences

- Click-accuracy tests (20/20 within the target control) become possible.
- This ADR is a **prerequisite for W1**; it must be reviewed before window
  targeting and UIA/Set-of-Marks work begins.
- Until W1.2 lands, the current fallback remains a known defect, not an
  accepted behavior.
